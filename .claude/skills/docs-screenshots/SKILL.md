# Documentation screenshots

Screenshots are generated by `scripts/docs_screenshots.py`. The process,
conventions, and sample data rules are documented in `docs/dev/screenshots.rst`.
Read that page first; it is the source of truth, and this skill only adds the
workflow.

## Workflow

1. **Find what needs updating.** List the images on the page
   (`grep -n 'image::\|figure::'`) and look at each one. Check
   `uv run scripts/docs_screenshots.py --list` to see if a screenshot already
   has a function.
2. **Agree on the plan** with the user before changing files: which images,
   which dashboard pages, and which data they will show.
3. **Check the instance.** Only one runs at a time (Community or Business).
   Ask the user to switch when needed; never start or stop containers yourself.
   The user provides the `sessionid` cookies; pass them as
   `RTD_COMMUNITY_SESSIONID` / `RTD_BUSINESS_SESSIONID` and never write them
   to files.
4. **Survey the page** before writing code: take a plain screenshot to see
   what the dev data looks like, and read the ext-theme template for labels
   and markup.
5. **Add or update a `@shot` function**, following the conventions in the
   dev docs (light theme, `example-user`, generic avatar, no dev URLs or
   secrets, sample data only in the browser). If your dev data differs,
   change `SOURCES`, not the functions.
6. **Review** with `--out <scratchpad>` first, look at every image (a
   `magick montage` contact sheet helps), then run without `--out` to write
   into `docs/user/`.
7. **Update the text** around each image to match the dashboard: exact labels,
   `:menuselection:` for navigation, `:guilabel:` for buttons and fields.
8. **Report** which images contain sample data, and any image that couldn't be
   generated (pages on GitHub, screenshots provided by someone else).

Don't commit or push; the user does that.
